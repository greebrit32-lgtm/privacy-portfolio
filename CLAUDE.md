# Privacy Portfolio — Working Rules

## About this repo
Public portfolio of entry-level Privacy Analyst work by Brittany Green (former HS teacher,
studying for CIPP/US and Security+). Three projects: 01 EdTech vendor review, 02 PIA/data map,
03 incident tabletop. Audience: hiring managers and privacy professionals.

## Data rules (non-negotiable)
- Public information and fictional data only. Never real student, staff, or patient data —
  not even "anonymized" real records.
- Fictional organizations (e.g., the district) must be clearly labeled fictional and must not
  share a name with a real district.
- Data inventories and data maps list **types** of data (e.g., "precise geolocation"), never
  sample records. If an example helps, make it obviously synthetic (e.g., "User A").

## Sourcing rules
- Every factual claim about a real vendor or about the law cites a source URL and the date
  accessed, using the source ID from that project's `sources/source-register.md` (e.g., [S03]).
- Cite the specific section/clause (e.g., "Privacy Policy §4, 'Sharing with Service Providers'";
  "34 CFR §99.31(a)(1)").
- If something cannot be verified from public documents, write
  "Not found in public documentation" — never infer, assume, or fill gaps from general knowledge.
- Prefer primary sources: statute/regulation text (eCFR, Texas statutes site), agency guidance
  (Dept. of Ed SPPO, FTC), the vendor's own pages. Secondary sources only for context, labeled.
- Note the effective/"last updated" date of each vendor document.

## Tone
- Neutral and factual about the real vendor. Findings describe what the documents say or do not
  say ("The policy does not specify a deletion timeframe"), not conclusions about the vendor's
  conduct or intent. No words like "violates," "fails," "illegal" — use "gap relative to
  [requirement]" or "not addressed."
- Include a disclaimer on every deliverable: independent educational exercise, public documents
  only, not legal advice, not affiliated with or endorsed by the vendor.

## Division of labor
- Brittany makes the judgment calls: risk ratings, approve/conditional/reject decisions, which
  findings make the memo. Claude drafts options, explains reasoning in plain language, and
  marks ratings as "PROPOSED — Brittany to decide" until confirmed.
- Tie concepts to CIPP/US Body of Knowledge topics (e.g., "FERPA — Education records & the
  school-official exception"; "COPPA — verifiable parental consent") and add a short
  "Study tie-in" note when a new concept comes up. Log these in `study-notes.md`.
- Explain, don't just produce: when drafting, say *why* something is a gap.

## Output formats
- Deliverables in Markdown (GitHub-renderable: tables, headings, no HTML-only features).
- Questionnaire as .xlsx, generated by `tools/build_questionnaire.py`
  (`python3 -m venv .venv && .venv/bin/pip install -r tools/requirements.txt`).
- Project 02 data inventory as .xlsx, generated by `tools/build_inventory.py` from
  `02-pia-data-map/working/` Markdown (same pattern: Markdown is the source of truth).
- PDF exports for LinkedIn via `tools/export_pdf.sh <file.md> [out-dir]` (pandoc → HTML →
  headless Chrome → PDF) into `deliverables/pdf/`.
- Memo must fit 2 pages in PDF.

## Working style
- Brittany works in 30–60 minute sessions. Each session has one clear goal and ends at a
  stopping point with a commit and an entry in `session-log.md` (done / next step / open questions).
- At session start, read the current project's `session-log.md` and pick up from "Next step."
  Each project's full session plan is in its own `README.md`.
- Keep scope small; propose before building anything large.
- Commit at the end of each session, never push without asking.
